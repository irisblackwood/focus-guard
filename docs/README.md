# 文档导读（docs/README.md）

> **状态**：权威 · 适用版本 3.5.3 · 最后核对 2026-11-26

> **本页回答「我该读什么」；[INDEX.md](INDEX.md) 回答「某份文档在哪」。**
> 分工是刻意的：INDEX 是**表**（按名字/任务查，可 grep），本页是**路**（不知道读什么时按角色走）。
> 两页都不抄数字、不抄版本、不抄状态——份数与落后几档看 [STATUS.md](STATUS.md)，那是唯一真值的渲染结果。

## 一、先选路

### A. 第一次接触，想判断「这东西要不要装」（30 分钟）

1. [README.md](../README.md) —— 30 秒速览，决定要不要往下看
2. [INSTALL.md](../INSTALL.md) —— 装。装不上再看这里，别的地方没有安装步骤
3. [ARCHITECTURE.md](ARCHITECTURE.md) —— **只读 §核心机制 的前四节**（空气层 / 触发层 / 梯度处罚 / 预算与进度检测），约 30 行，够建立心智模型
4. [STATUS.md](STATUS.md) —— 哪些文档自己承认落后，一眼看完

到此为止。剩下的读了也用不上，因为没有具体要改的东西。

### B. 要改判定链（半天）

顺序不能反：**先知道边界，再知道怎么判，最后才看代码。**

1. [DESIGN-CONSTRAINTS.md](DESIGN-CONSTRAINTS.md) —— 十一条约束，每条都带「不做会怎么坏」
2. [THEORY-BASIS.md](THEORY-BASIS.md) —— 上面那些约束从哪来。**与上一份配对读**，前者给判据、后者给来源，两页互不复制
3. [RULES.md](../packages/core/docs/RULES.md) —— **第二部分速查表**先看（奖惩明细，一页），再进**第三部分技术映射**（条款 → 钩子实现）
4. [ARCH-MAP.md](../packages/core/docs/ARCH-MAP.md) —— 每块能力现在什么状态、代码锚点在哪、缺口在哪
5. [ARCHITECTURE.md](ARCHITECTURE.md) —— 现在可以全文读了；§设计取舍与已知边界在末尾

**别跳第 1 步。** 这个仓里最贵的一类返工，是「改完才发现某条约束正好禁止这么改」。

### C. 要发版、要记账（一小时）

1. [RELEASE-POLICY.md](../packages/core/docs/RELEASE-POLICY.md) —— 什么时候 bump、什么算「修复」
2. [VERSION-PLAN.md](../packages/core/docs/VERSION-PLAN.md) —— **计划的唯一载体**。排期只在这份维护
3. [CHANGELOG.md](../CHANGELOG.md) —— 变了什么。写之前先看 [WRITING-STYLE.md](../packages/core/docs/WRITING-STYLE.md) 的排版判据
4. [PROFILE-TUNING.md](../packages/core/docs/PROFILE-TUNING.md) —— 只有要调画像参数时才需要；它是**人工批准制**台账，不是自动调参入口

### D. 被拦了、想申辩

1. [RULES.md](../packages/core/docs/RULES.md) **第二部分速查表** —— 我犯的是哪一条、罚到哪一档
2. 同文件 **第三部分技术映射** —— 拦我的那条对应哪段代码，有没有实现偏差
3. 运行时镜像技能 `focus-rules` —— 与法条同源，按需加载

## 二、文档为什么分三处放

这是新人第一个疑问，也是最能省时间的一个答案。

| 层 | 位置 | 管什么 | 谁读 |
|---|---|---|---|
| **对外门面** | 仓根 | 装得上、用得对、变了什么 | 用户、新用户 |
| **项目治理** | `docs/` | 为什么这么设计、边界在哪、现在什么状态 | 改判定链的人、交接的人 |
| **包内技术** | `packages/core/docs/` | 法条、能力地图、计划、基准 | 改代码的人 |

分层理由不是审美：

- **对外的不该被内部实现细节污染**——README 讲清「装什么、怎么用」就够，机制正文 3.4 版已迁出到 `docs/ARCHITECTURE.md`
- **治理层跨包**——它同时管 `packages/core`、`packages/extended`、`packages/adapters`，塞进任何一个包都变成「某个包的文档在讲别的包」
- **包内文档跟包走**——随 npm 发布或至少随包演进，读者是拿到源码的人

**新文档该放哪，一条判断规则**：

- 用户装完就要用的 → 仓根
- 跨包成立，或需经批准才改的 → `docs/`
- 只对这个包成立、随包发布的 → `packages/core/docs/`

## 三、逐份说明

### 3.1 对外门面（仓根）

- **`README.md`** —— 回答「这是什么、装不装」。读完该能决定装或不装。**别拿它当机制说明**：机制在 `docs/ARCHITECTURE.md`，README 只留入口。
- **`INSTALL.md`** —— 唯一安装源。装、卸、装坏了都看这里。**别拿它当配置说明**：34 个环境变量的唯一清单在 `docs/ARCHITECTURE.md` §配置。
- **`CHANGELOG.md`** —— 回答「变了什么」。升级前、怀疑回归时读。**别拿它当计划**：为什么这么改、排到哪，在 `VERSION-PLAN.md`。
- **`CONTRIBUTING.md`** —— 提交规矩与 CLA。要提 PR 才读。
- **`HANDOFF.md`** —— **标着「归档」却还在根目录，且 `INDEX.md` 里查不到它。** 留着有两个硬理由：`src/dsh/seams/session-start.mjs` 在会话启动时按这个路径做交叉巡视（存在性检查），且源码里有 15 处以「HANDOFF §八/§九/§十」为锚点的注释。**别读它当现状**，正文是 3.0.5 时期的。

### 3.2 项目治理（`docs/`）

- **`ARCHITECTURE.md`**（438 行）—— 回答「怎么运作」。核心机制 / 配置（34 个环境变量）/ 工作原理（含常驻注入体量、前缀稳定性）/ 测试与质量闸 / 双包架构 / 设计取舍。**第一次来只读前四节**。别拿它当判定依据——法条在 `RULES.md`。
- **`DESIGN-CONSTRAINTS.md`**（321 行）—— 回答「改之前不能碰什么」。十一条约束 + 失效模式 + 落点。**判据只有一条准入规则：说不出「不做会怎么坏」的，不进这页。**
- **`THEORY-BASIS.md`**（210 行）—— 回答「约束从哪来」。七层理论、脑区归类、记忆与神经元机制、文献清单。**它是脚手架，不是物理学**——提供约束，不提供验收标准。
- **`GOVERNANCE-LAYERS.md`**（162 行）—— 回答「五层治理离目标还差什么」。现状 → 目标的差异登记与排期，**不改代码**。状态是「参考」且核对日期较旧，读前看状态头。
- **`INDEX.md`** —— 查：按名字或任务找到某份文档。**它是表，不是路**；不知道该读什么时回到本页。
- **`README.md`** —— 本页。

### 3.3 包内技术（`packages/core/docs/`）

**判定依据**

- **`RULES.md`**（501 行，v1.2）—— 法条全本。第一部分 21 章正文、第二部分奖惩速查、第三部分条款→钩子映射、第四部分常驻注入（逐字镜像）、第五部分项目结构、第六部分立法法。**「适用版本」记的是最后一次修法时的产品版本，长期落后是常态，不是欠债。**
- **`LEGISLATION-LAW.md`** —— 立法程序。要改法条才读，规矩是「不许一边改判据一边宣布自己合规」。
- **`THREAT-MODEL.md`** —— 回答「哪些漏洞要修、哪些按判据不修」。判据是「**不防攻击者，防插件自己把用户的机器/数据弄坏**」。含**三条明确不做**（属主校验 / 状态签名 / `FG_PYTHON` 白名单）——**别再把它们当缺口翻出来**。
- **`RETIRED.json`** —— 退役台账：记「哪个名字已经不叫这个了」。改名前先加一条，改完跑 `npm run legacy:audit`，红了就是漏改。**它是唯一记得旧名的地方**，代码和文档都不记得。

**状态与计划**

- **`ARCH-MAP.md`** —— 能力状态 + 代码锚点 + 缺口。**「这块做到哪了」以它为准。**
- **`VERSION-PLAN.md`** —— 计划唯一载体，含测试债务分档与退出判据。改计划要同时改本文件与 `ARCH-MAP.md` 的版本路线行。
- **`MCP-4.0-PLAN.md`** —— 4.0 常驻形态调研，**未开工**。结论先行：MCP 能当「体」，当不了「神经」——工具拦截的官方入口仍是 hooks。
- **`MEMORY-4.5-PLAN.md`** —— 记忆系统独立与 4.5 规划。**与实现尚未同步**，裁决仍以 `ARCHITECTURE.md` 与 `VERSION-PLAN.md` 为准。
- **`MEMORY-HYBRID.md`** —— 记忆检索该不该上向量、怎么接。三档（全量/向量/混合）× 四档规模的定量对比 + 四阶段迁移。**核心结论：当前规模不值得上检索；真要上，检索做成按需工具，不做自动注入**（自动注入会毁掉前缀稳定）。

**工程规矩**

- **`RELEASE-POLICY.md`** —— 版本面与「修复」的受众判据。发版前必读。
- **`WRITING-STYLE.md`** —— 文档排版判据，**也管对话回复**。写任何 md 之前扫一眼。
- **`HOOK-ORDERING.md`** —— 钩子定序核查：四条路与各自代价。只有在动挂载顺序时才需要。
- **`PROFILE-TUNING.md`** —— 画像参数回流台账，**人工批准制**。禁止无人批准的自动调参。

**测量与台账（读前看数据截止日期）**

- **`BENCH.md`** —— 五类基准，各回答一个问题。**延迟与 token 数字是快照，引用前看日期。**
- **`MEMORY-RECALL-EVAL.md`** —— 结构化记忆 vs 向量检索的离线召回评测。**向量是 TF-IDF 稀疏向量，不是语义向量**；qrels 是词项启发式，只看相对差、不看绝对值。
- **`AB-PROMPTS.md`** / **`AB-SESSION.md`** —— A/B 采集协议与一次会话记录。协议可复用，数字是当时样本。
- **`deepseek-pricing-audit.md`** —— 价目核对底稿，是常量的来源，**不是现行报价**；改价先重核官方页。

**渲染实现**

- **`BRAIN-VIZ.md`** —— `.focus-guard/brain.html` 里的东西怎么画出来的。为什么这么设计看 `DESIGN-CONSTRAINTS.md`，数据层看 `MEMORY-4.5-PLAN.md`。

### 3.4 自动生成，别手改

| 文件 | 生成命令 | 手改会怎样 |
|---|---|---|
| [STATUS.md](STATUS.md) | `npm run docs:status` | `docs:lint` 判 `status-table-stale` |
| [MODULES.md](MODULES.md) | `npm run modules:sync` | pre-commit 重生成时覆盖 |
| `book.html` | `npm run docs:book` | 生成物不入库（已进 `.gitignore`），所以这里只写文件名、不给链接 |

这三份的共同点：**真值不在它们身上**。状态的真值是每份文档开头那行 `> **状态**：…`；模块的真值是 `modules-list.mjs` 里的路径清单。改真值，再重生成。

### 3.5 归档与外部摘录：怎么读

- **`archive/`**（10 份）—— 已过期的交接与总纲。**唯一用途是回答「当时怎么想的」**，不能作为现状依据。出口规则在 `INDEX.md` 第三节：超 30 天未更新 / 对应版本已发布 / 已被取代，满足任一即移入。
- **`vault-notes/`** —— 外部资料摘录（厂商研读 + FG3 要点）。正文被 `.git/info/exclude` 屏蔽，仓内只有题录。**非项目事实源，不作裁决依据。**

## 四、三份最容易混的文档，边界在这

新人最常问「这三份是不是重复了」。不是。

| 文档 | 只回答 | 真值归属 |
|---|---|---|
| `RULES.md` | **能不能做、做了怎么罚** | 判定依据的唯一来源 |
| `ARCHITECTURE.md` | **机制怎么运作** | 机制与边界的唯一来源 |
| `ARCH-MAP.md` | **做到哪一步了** | 能力状态与代码锚点的唯一来源 |

三处内容重叠时**以职责归属为准，不互相抄更新**。抄一次就是两份真值，二十天后必然分叉——`INDEX.md` 自己就吃过这个亏（手抄状态列，实测 18 处与源不符）。

## 五、这份导读怎么防腐化

本页刻意**只写不容易变的东西**：

- 不写份数、行数、版本号、落后几档 —— 这些看 `STATUS.md` 与 `MODULES.md`
- 不写「当前状态是 X」 —— 状态看每份文档自己的状态头
- 只写「它回答什么问题 / 什么时候读 / 别拿它干什么」 —— 这三样跟着**文件的存在理由**走，不跟着内容走

仍然会腐化的只有一样：**新增文档时没人记得往这里加一行**。

所以维护规则是硬的：**新增权威文档必须同时进本页与 `INDEX.md`**；删除或归档时两页一起改。
判断一份文档该不该在本页出现，看它是否回答了一个**别人会问的问题**——回答不了的，它本身就该被删掉。
