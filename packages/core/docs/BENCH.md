## 〇、任务测试（task bench，50 组）

判定基准测"单条判定"，任务测试测"**一整件任务**能不能走通"：一组 = 一串真实调用
（读 → 改 → 跑测试 → 查日志），任何一环被错拦整组即失败。数据在 `tests/task-suite.json`。

覆盖 6 类：只读探查（T01-T10）、代码修改（T11-T18）、命令执行（T19-T30）、
高危操作（T31-T36）、资格闸（T37-T41）、边界与误伤敏感（T42-T50）。

```
50 组 / 57 次调用     组通过率 100%     调用准确率 100%
误伤 0     漏拦 0     延迟 p50 2.04ms / p95 67.24ms
```

`--group T31` 单跑一组，`--json` 机器读。首轮（修复前）与修复后的对照见 CHANGELOG「未发版」节：
`psql -c 'DROP DATABASE'` 曾被引号豁免漏拦、`rm -rf ./dist` 与 `/tmp/...` 被资格闸误伤、
`Write` 到 `C:\Windows\...` 未被系统路径闸拦——四处都由这套测试发现并修掉。

### A/B 对照（FG 关 vs FG 开）

`npm run bench:tasks -- --ab` 跑两遍同一套任务：A 组直通（等价于插件禁用），B 组走真实判定。

```
A 组（FG 关）  可完成 57/57   延迟 p50 0ms / p95 0ms
B 组（FG 开）  合规   57/57   延迟 p50 2.09ms / p95 68.09ms
FG 介入        15 次拦截（应当拦 15 / 误伤 0）
热路径开销     p50 +2.09ms / p95 +68.09ms
```

- 「应当拦 15 / 误伤 0」是目前的口径：15 条拦截全部落在任务集标注为「应拦」的调用上
- p95 的 +68ms 是**新命令首次**付哨兵冷启动；重复命令走缓存（见第一节）
- `--control` 只跑 A 组

### 纯净 A 组（零 FG 导入，`npm run bench:control`）

上面 `--ab` 的 A 组只是"把闸跳过"，**FG 模块仍被 import**。要真正纯净用独立进程跑：

```
A 组（纯净）：50 组 / 57 次操作
  实际执行    27（真实 fs 操作）
  仅记录      30（Bash 命令，控制组不实跑）
  失败        0
  延迟        p50 0.323ms / p95 0.842ms（无任何闸）
  FG 模块加载  0
```

纯净性由三条硬约束保证，脚本自校验：

1. **不 import 任何 `packages/core/src/` 模块**——文件里出现 `from '…src/…'` 即 exit 2
2. 不读 FG 状态、不写审计、不注入系统提示
3. **Bash 一律不实跑**，只记录（夹具目录不是仓库、Windows 无 `ls`/`pwd` 语义，实跑只会制造无关噪音）

对照结论：无闸时 57 次操作全部可完成、延迟 p50 0.32ms；有 FG 时同样 57 次全部合规，介入 15 次，p50 +2.09ms。

若要**会话级**纯净（真 agent 会话、真 token 统计），本安装没有 `dsh headless`（已实测回落到 web 的帮助），
只能手动开一个未安装 FG 的 profile 跑同批任务——那属于人工 A/B，不在脚本范围内。

## 一、判定基准（decision bench）

固定 15 条用例 × 10 轮 = 150 次真实 `preExecuteListener` 调用，覆盖：

- **红线层**：`rm -rf /`、`git push --force`
- **第 1.5 层**：环境替代（`cat` → `bat`）
- **第 1.4 层**：整文件读取闸（>300 行无 offset）
- **体积闸**：`Grep content` 无 `head_limit`
- **资格闸**：`npm publish` 无授权
- **取证闸**：有会话状态、未读即改；另有"无状态文件 fail-open"对照用例
- **不得误伤**：`ls -la`、`git status`、写新文件、分段读

输出三个指标：

```
准确率   100.00%
误伤率   0.00%（期望放行却被拦）
延迟     p50 0.46ms / p95 7.37ms / max 8.26ms      ← 2026-10-29 快照
```

**基线**：`packages/core/docs/BENCH-BASELINE.json`。`--update` 覆盖（`_latencyNote` 由脚本写入，不会丢）。
不达基线（准确率掉 2 个点以上、**p50 超基线 ×2**、或 p95 超 100ms）即 exit 1。

**为什么相对回归看 p50 不看 p95**（2026-10-29 修）：延迟是**双峰分布**——5 个 Read/Grep 用例
6.9–8.0ms，其余 10 个 0.16–0.84ms；5/15 ≈ 33% 的样本落在慢峰，所以 p95 必然停在 7–8ms 一带。
p50 落在快峰（0.5ms），更能代表「典型一次判定」的成本。容差 ×2 能抓住「整体变慢一倍」。

| 用例 | p50 | p95 |
|---|---|---|
| `small-file-allow` | 8.04 | 8.70 |
| `whole-file-deny` | 7.49 | 8.61 |
| `grep-broad-dir-deny` | 7.14 | 8.76 |
| `grep-narrowed-allow` | 7.11 | 8.12 |
| `whole-file-offset-allow` | 6.91 | 8.03 |
| 其余 10 条（Edit / Bash / 无状态） | 0.16–0.84 | ≤1.38 |

**7–8ms 的成因未定位**。已排除三个假设：`statSync`（实测 0.017–0.026ms）、状态文件新建/复用
（固定会话 + `clearSession` 后仍 7.5ms）、`saveState` 的 `rename`（改成直写后仍 8.0ms）。
下一步该查 `volume.mjs` 的三闸（`judgeReadGate` / `judgeGrepGate` / `judgeCatGate`）——
慢的 5 个用例全是 Read/Grep，而 Edit / Bash 类都在 1ms 以下。

> **撤回两个数**：早先注释里写过「固定 sessionId 对照 p95 1.03ms」「真实热路径 1.16ms」。
> 那两个是在**行为错误**状态下测的（9 个用例串味、准确率 94%），不能引用，已删。
> 另：旧基线 p95 = 2.37ms 与 byCase 里 7.3ms 的用例自相矛盾（整体 p95 不可能低于所有用例的 p50），
> 已随本次重定一并作废。

#### 四、主指标与参考指标

- **主指标：未缓存输入 / 会话。** 它只数真正新算的 token，不被步数操纵。

- 禁用指标：「每步 token」「每步成本」——分母被步数稀释，方向可能反。

#### 五、判定规则

| 未缓存输入中位数 | 成本中位数 | 判定 |
|---|---|---|
| 降 ≥10% | 不升 | **FG 有正收益** |
| 持平 | 升 | FG 是纯摩擦 |
| 上升 | 升 | FG 有害，需查误伤 |

#### 六、禁止清单（每一条都是踩过的坑）

- ✗ **用合成参数**：`output_mode` / `head_limit` 真实工具不存在（`session-002c143b` 实测）。
  夹具参数必须来自真实调用记录。
- ✗ **跨峰谷价比较**：周日谷价 vs 周一峰价，成本不可直接比。
- ✗ **用「每步」指标下结论**：3 步 vs 9 步，分母不同。
- ✗ **单看命中率**：拦截导致步数变多，会把命中率机械抬高。

## 四、威胁评测

`npm run eval` 跑的是 **ZCode 路径**（`hooks/guard.mjs`）的攻击样本集。
DSH 原生插件的判定基准看第一节，两者互补：一个测规则覆盖面，一个测链路准确率与延迟。
