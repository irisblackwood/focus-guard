### 1.3 三条结论更正（把我之前的说法改准）

**① 棘轮顶格不是"许可证"，是最严状态。** 我之前说"顶格 = 涨到上限为止的许可"——错了。
实测 8/8 意味着**零余量**，新增一条即红。真正的问题是**存量从来没降过**：闸门只能防涨，
没有任何东西催还。所以 B 不是调阈值，是补一条**还款义务**。

**② `hooks/guard.mjs` 不是死代码。** 我之前把它当"封存层死代码"。查 `packages/core/hooks/hooks.json`：
六处钩子（SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / PostToolUseFailure / Stop）
全部指向它——它是 **Claude Code / ZCode 宿主的活入口**，只是 DSH 不走它。
真正的问题是两个身份叠在一起：它既是"活入口"，又是 `threat-eval` 的**被测对象**，
而 DSH 的活路径 `src/dsh/` 反而不在任何威胁评测里。C 已经把这条边界写进输出，但**补覆盖**另立项。

**③ E（工具分界）待做，不是忘了。** `tools/` 里混着两类东西：
插件自身工具（`lint` / `smells` / `schema-fingerprint` / `privacy-guard`）与
作者私有资料工具（`library-build` / `library-book`）。后者操作的是 `.ai/` 下的私人笔记，
对任何其他使用者都无意义。分法有两条，需要拍板：
① 物理拆包（`tools-private/`，分发时删）；② 只在文件头标注"私有工具，不属运行时能力"。
**我倾向 ②**——零迁移成本，且拆分会让 `check` 链对两种使用者给出不同结果。

**④ D（路径收敛）是 3.4 的主体，代价已测绘。** 309 处引用 / 45 个文件；
生产层约 97 处（`src/` 46、`hooks/` 9、`tools/` 40、`extended/` 2），测试层约 210 处。
仓库**没有路径常量层**（`constants.mjs` 里只有两个拦截正则）。三个风险点：
`guard.mjs` 的 `LIBRARY_RE`/`BLOCKS_RE`（改错要么拦死合法写入、要么停止保护）、
`.focus-guard/` 运行态（2.2 MB 哈希链 `AUDIT.log`，DSH 可能正在写）、
`docs/vault-notes/README.md`（被跟踪的空壳清单，就在要搬的目录里）。
分两阶段：**Stage A** 建 `paths.mjs`、值仍指当前位置（零行为变化）；**Stage B** 翻转常量 + 迁数据 + 改断言。

### 1.4 3.4 补充项（2026-10-31）

> ①② 源自 Claude Code 提示词复核；③ 源自 hook 协议层复核。

#### ① 回合出口（**已完成 2026-10-31**）

现状：FG 只有**被动终止**——预算耗尽、熔断触发。而预算耗尽时，动作已经烧完了。

参照 `claude-code/prompts/plan-mode.md` 的封闭集合约束：

> your turn should only end with either using the AskUserQuestion tool OR calling ExitPlanMode

**照搬不了**：DSH 的 `agent/turn-stopping` 不提供 `stop_hook_active`，打回会强制续跑死循环
（`stopGuard.mjs` 头注释取舍①已记，本人被自家熔断拦过）。所以「出口」降一档——
**不要求怎么结束，要求承认怎么结束的**。

| 项 | 决定 | 理由 |
|---|---|---|
| 出口形态 | 收尾一句「剩下什么没做」即可，不指定工具 | DSH 无工具级出口信号 |
| 不满足时 | 审计 `turn-cut-short` + 警告一次，**不拦** | 拦会死循环 |
| 与预算的关系 | 预算先耗尽先拦；出口检查在**收尾时**做，不前置 | 出口是收尾语义，不是执行语义 |

判定在 `core/stopPolicy.mjs` 的 `needsCutShortNotice({text, state})`——只在 `stopBlocked` 时触发，
已声明熔断或已说明未完成的放行。执行在 `stopGuard.mjs` 的 `handleCutShort`，报完清 `stopBlocked`，不重复提醒。

#### ② 默认沉默（**不做**，前提不成立）

我 2026-10-31 提出「FG 的旁路观察者按规则报、不按后果报，所以才会一直重复」。**核实后这句话是错的**：

| 观察者 | 实际行为 |
|---|---|
| `compactionWatch` | 头注释纪律①「绝不写 surface、绝不 append、绝不 cancel」，只写审计 |
| `heartbeat` | 每 10s 覆写 `status.json`，不碰会话 |
| `postProgress` | 写审计；异常时 `warn()` 到宿主日志，不注入 |
| `systemPromptListener` | 唯一注入层，只追加**成本行** |

**FG 本来就不打扰用户。** 「一直重复」是 AI 的输出行为问题，不是插件机制问题。给不存在的问题写代码 = 防御性设计。

留痕理由：避免下次又把它当缺口提出来。

#### ③ 协议层泄漏：宿主方言判定漏在 `guard.mjs`（**排 3.4.0**，2026-10-31 记录）

`hooks/protocol.mjs:2` 自述「harness 专有环境变量只出现在本层」。实测：**环境变量守住了，载荷形态没守住。**

```
// guard.mjs:960
const dshBridge = respText === undefined && (input.transcript_path === "" || input.transcript_path === undefined);
```

这是 DSH 桥的 Stop 载荷方言（`transcript_path` 恒为空串且无收尾文本），属 harness 专有知识，却写在执行体里。
`:956`、`:958` 两行注释记录了 2.5.0 与 2.5.2 两次为它打补丁——**补丁有累积迹象，是分层失效的典型形态**。

| 项 | 决定 |
|---|---|
| 排期 | **3.4.0**，与 N4 契约探针同批 |
| 为什么同批 | N4 断言「载荷含 `turn`/`step`」，与本条同属「载荷形态知识」——一并归位，探针才有单一真相源 |
| 做法 | `protocol.mjs` 导出 `isDshBridge(input)`，`guard.mjs` 只调用不判断 |
| 验收（可复跑） | `rg 'transcript_path' packages/core/hooks/guard.mjs` 只命中调用处，不命中判定逻辑 |
| 4.0 之后 | 该判定随 `guard.mjs` 迁入 MCP 内核 adapter，**不保留在协议层** |

**为什么现在不动**：4.0 会整体重写 `guard.mjs`（废除外挂脚本 Hook），提前拆不如一次到位。
**为什么仍要记**：4.0 之前 `guard.mjs` 还会继续改，留着破口就会继续往执行体里堆方言补丁；
且接第三个 harness 时，这类补丁会线性增长。

#### ① 前缀稳定模块没接线（`prompt-prefix-shift` 恒 0 条）

`packages/core/src/core/prefixStability.mjs`（2026-10-29 建）导出了 `fingerprintSections` / `isFgSection`，
注释写着「每步算一次 FG 段指纹，变了就写一条 `prompt-prefix-shift` 审计」。

**生产代码零引用。**

| 证据 | 值 |
|---|---|
| 引用处 | 仅本文件自身（`:88`、`:118`） |
| `AUDIT.log` 中 `prompt-prefix-shift` | **0 条** |
| 真实会话漂移 | 10-27 三个会话中 **2 个 DRIFT**，分歧点恒定在 9624（`[FG-WORKSPACE]` 段） |

漂移实证（`4cbe896a`，32 步，**同一会话中途**）：

```
A: 上次会话：session-c00d · 工具调用 116 · 被拦 0 · KPI -181
B: 上次会话：5a292b3a-7e1 · 工具调用   4 · 被拦 0 · KPI  -5
```

原因是**并发**：另一个会话结束时更新了卷宗，正在跑的会话下一轮就读到新值。
前缀从 9624 起全部失效——而审计里一条都没记。

| 待定三点（须批示） | ① 在哪一步算（注入后 / 请求前）② 首次算不算基线 ③ 漂移时只写审计还是同时告警 |
| 验收（可复跑） | 人为制造一次卷宗变更 → `AUDIT.log` 出现 `prompt-prefix-shift`；正常会话 0 误报 |

#### ② **P0-1** 系统临时目录残留（**已完成 2026-11-01**）

实测 `%TEMP%` 下 `focus-guard-*`：

| 项 | 值 |
|---|---|
| 文件数 | **11,856** |
| 总大小 | 1.8 MB（单文件极小，**是数量问题不是体积问题**） |
| 时间跨度 | 最早 2026-10-25，全部在 7 天内产生 |
| 均值速率 | **≈1,700 个/天** |

形态分布（前三类占 92%）：

```
6,933  focus-guard-vg-<PID>-<N>.json        58.5%
2,555  focus-guard-shell-*.json             21.5%
1,496  focus-guard-poststate-*.json         12.6%
 872   其余（session / test / eval）
```

**根因**：`core/state.mjs:16` 的 `statePath()` 硬编码 `join(tmpdir(), ...)`，**没有环境变量覆盖**。
同文件 `casePath()` 有 `FG_CASE_FILE`、`core/audit.mjs` 有 `FG_AUDIT_FILE`，**唯独状态文件没有**——
于是 730 个测试每个都往系统临时目录写一份，且不删。

**为什么没被清掉**：`cleanStaleTemp()`（`state.mjs:89`，第六十一条落地）只删 **30 天未动**的。
现存全部在 7 天内，一条都够不着。按当前速率，30 天后稳态约 **5 万个**。

**命名问题**：测试残留与生产状态文件**同前缀同扩展名**，肉眼分不清哪些是运行态，
人类无法区分哪些是运行态、哪些是跑测试留下的垃圾。

| 项 | 决定 |
|---|---|
| 做法 A（断源） | `statePath()` 加 `FG_STATE_DIR` 覆盖；测试基座统一指向一次性目录 |
| 做法 B（兜底） | `cleanStaleTemp()` 增加按数量上限清理（如 >5,000 个则按 mtime 从旧删到 2,000） |
| 不做 | **不删现存 11,856 个**——位于个人目录，须人类明确确认后另行处理 |

#### ②-补 **P0-1 残余面**（已完成 2026-11-01，同批）

上面那批只解决了「量」。「彻底」要再答三个问题，逐个交代：

**(1) 为什么清理总能被写入量甩开？** —— 因为判据是年龄，年龄不约束写入。
`cleanStaleTemp` 从 30 天改到 7 天只是把斜率改小，**结构没变**：只要再出现一条「每次测试写一份」的
路径，7 天窗口照样堆满。补 `STATE_FILE_CAP = 500` 上限判据——它与写入量无关，是唯一能给稳态上界的东西。
当前会话文件豁免淘汰（活跃会话若长时间不写状态，光看 mtime 它就是"最旧"的，被上限误删＝清空熔断状态）。

**(2) 状态文件该不该放在临时目录？** —— 该，但**目录要私有**。
`fused` / `probation` / `rejectedCmds` 是熔断决定的输入，而 `mkdirSync` 默认 mode 在 POSIX 上是 0o755，
落共享 `/tmp` 时同机他人可读（CWE-377）。改为 0o700（`state.mjs::saveState`、`audit.mjs` 两处）。
Windows 忽略 mode，无害。

**(3) 中间文件为什么是漏洞？** —— `path.<pid>.tmp` 可预测 + `writeFileSync` 跟随符号链接。
同机他人预置链接 → 改写任意目标文件（CWE-377 / CWE-59）。改为 6 字节随机名 +
`openSync(…, 'wx', 0o600)`：`wx` = `O_CREAT|O_EXCL`，**已存在即失败且不跟随链接**；
随机名让路径无法被预置。两条合起来，"预测到文件名"不再是攻击前提。

**同一形态但按不同处理的一处**：`saveCaseRecords` / `saveLedger` 仍是 `.<pid>.tmp`。
判据是**目录是否共享**——它们落在项目自己的 `.ai/`，能往那里放符号链接的人已经能直接改卷宗，
加随机名是零收益的复杂度。已在代码注释里写明理由，避免后人当遗漏来"修"。

**第七例「写了但没连上」**：上一批把状态文件迁进 `stateDir()` 后，`acceptance.test.mjs` 的
「不遗留 .tmp 残片」断言仍扫 `tmpdir()` 根——**变成恒真**，照绿但什么都不测。已改扫真实落点。
这是同一形态的第七次（前六：`SESSION_RULES_FULL`、`prefix-audit` 锚点、`prefixStability`、
`after` 钩子、docs 台账、测试 tmpdir 断源只做了一半）。

| 项 | 落点 |
|---|---|
| 上限判据 | `state.mjs::purgeStaleIn(dir, cutoff, cap, protect)` + `STATE_FILE_CAP` |
| 目录权限 | `saveState` / `audit.mjs` 的 `mkdirSync` 补 `mode: 0o700` |
| 原子写加固 | `saveState` 改随机名 + `openSync('wx', 0o600)` + `writeSync` |
| 孤儿回收 | `TEMP_ENTRY_RE` 补 `\.tmp`（进程被 kill 留下的中间文件） |
| 断言复位 | `acceptance.test.mjs` 改扫 `stateDir()` |

**验收实测**：`node --test tests/acceptance.test.mjs` → 102/102 pass；
另用一次性目录探针复验：600 个超额文件 + 1 个当前会话 → 清理后 501（当前会话受保护）；
把当前会话文件 mtime 拨到 8 天前 → 仍被过期规则删掉。

**没做的（如实申报）**：`readGuardState()` 的**目录扫描**分支仍取「mtime 最新的
`focus-guard-*.json`」，理论上可被塞文件影响判定。但生产路径走 `readGuardStateExact()`
（`evidence.mjs:185`，按会话 id 精确定位，**绝不做目录扫描**，3.0.8 已改），扫描分支只服务自检。
不为一条不在路径上的分支加平台分支判断——那是用复杂度换一个用不上的保证。

> 来源：[`DESIGN-CONSTRAINTS.md`](../../../docs/DESIGN-CONSTRAINTS.md) 的七条约束。

**前置核实结果（2026-11-11，结论：不成立）**：`model` 不是「模型 id」，而是第 5 层的**探针函数**
（`checkEligibility.mjs:81` `({command,purpose,scope}) => {mismatch,risk,reason,actual_effect}`）。
真实路径三处调用点**一个都不传**：

| 调用点 | 实际传参 |
|---|---|
| `adapters/dsh/eligibility-gate.mjs:276` | `model = null`（形参默认值，`gateToolCall` 的调用方也没传） |
| `dsh/tools.mjs:72`（`fg_apply` 通道） | `model: null` 显式写死 |
| `dsh/guard/authz.mjs`（pre-execute 资格闸） | 不传 → 走默认 `null` |

于是 `checkEligibility.mjs:232` 的 `if (typeof model === "function")` 恒假，第 5 层**整段跳过**。

**原表述需更正**：本节原写「未注入 model 时返回 `model-unavailable`」——不对。`model-unavailable`
只在**注入了函数但调用抛错/返回坏值**时产生（`:236` / `:239`）。未注入时 `modelSignal` 保持 `null`，
连 `skip` 都不记，是「第 5 层不存在」而不是「第 5 层判了 skip」。

**所以 C6 的正确前置不是「确认注入」，而是「先给第 5 层接一个探针」**。而探针必须由宿主/适配层提供
——FG 自己没有调模型的能力，也不该为此引入一个（那会把零依赖内核变成需要 API key 的东西）。
在探针接上之前，影子判定没有可补跑的对象，C6 做了也是空壳：与 `PROFILE-TUNING.md §四` 空表、
`schema:verify` 空转同病。**撤出排期，不占版本位；前置变化时再登记。**

**只补跑 `eligibility` 一路**（保留，供前置成立后参照）：影子判定成本必须可控。全跑 `PRE_STAGES` 等于取消短路，
常态成本翻八倍；只补跑最可能与红线冲突的那一路（语义），成本只在 deny 时发生。

**边界**：不改 `PRE_STAGES` 顺序、不改任何 verdict、不新增拦截。影子通道自身异常只 warn，
按原语义 fail-open，不影响当次决策。
