# 版本策略（RELEASE-POLICY）

> **状态**：权威 · 适用版本 3.5.3 · 最后核对 2026-11-19

> 2026-10-22：**每 10 次修复合为一次变更（x.x.0）；其余按补丁号递增**。

## 一、「修复」的定义（受众判据）

> 2026-10-27：**对外文档的「修复」默认指「修复用户可能已经遇到的问题」。**

对外文档写「修复某某问题」，等于向读者宣称一件事：**你可能已经踩过这个坑**。所以这三个字有门槛，三条同时成立才算：

| # | 条件 | 判据 |
|---|---|---|
| 1 | 缺陷存在于**已对外分发**的版本 | 版本号 ≤ **各对外渠道的最高版本**（见下方「渠道清单」，取最高者） |
| 2 | 用户有路径真的遇到 | 能在该渠道的公开产物上复现，不依赖只在本地未推送代码里存在的东西 |
| 3 | 修完之后对外可见行为变了 | 用户升级后能感知到差异 |

不满足第 1 条的叫**开发期缺陷**：在尚未发布的版本里被发现并处理掉。
它**不是「不算修复」**——技术上就是修复；它只是**没有用户受害**。

### 处置

| 场景 | 对外文档（`CHANGELOG.md` / Release Notes / `README*`） | 内部台账（`docs/HANDOFF-*.md`） |
|---|---|---|
| 缺陷在已发布版本里 | 写「修复」+ 影响面（哪些版本、什么症状） | 写「修复」+ 根因 + 证据 |
| 缺陷在未发布版本里 | **不写「修复」**：写「某某改为…／收敛为…／加固…」+ 事实 | 照写「修复」，注明「开发期，未发布」 |
| 不是缺陷（新增能力／重构／测试） | 按性质写 `feat` / `refactor` / `test` | 同 |

### 标注粒度：段级 vs 条目级

| 段落情况 | 怎么标 | 本仓实例 |
|---|---|---|
| 整段都只在未推送的代码里存在过 | 段首写 `> **影响面：开发期**` | 同质段落，省得逐条标 |
| 段内混合：有的修已发布版本的缺陷、有的是开发期新造的东西 | 逐条标 `〔开发期〕`（开发期那条）与 `〔影响面：x.y.z〕`（已发布那条） | **`3.2.0`**：熔断 / 抽查B / 审计重复记账 修的是 `3.1.0`（已推 GitHub）里的问题；工具链四件是当天新造。**`3.3.0`**：两条 `fix` 标 `〔影响面：3.2.1〕`，其余为新增能力 |

**未发布段的每条 `fix` 必须二选一自报影响面**，缺一条就报 `unattributed-fix`。
判据从段级改成逐条（2026-10-30，执行层结论，待批示）有两个原因：

1. **段级会放过**：段里只要有一处 `〔开发期〕` 就算合规，同段另一条开发期缺陷照样能写「修复」。
2. **段级会误报**：`3.3.0` 段一条开发期缺陷都没有（两条 fix 改的是已推 `3.2.1` 里的 `notePrefixShift`
   盲区与 `MAX_RENDER=1200` 裁剪，两者都在 `origin/main` 上），却被报「一处标注都没有」——
   两种完全不同的情形压成同一句红，红得没信息量。

`〔影响面：x.y.z〕` 里的版本必须 ≤ 已分发最高版，写高了报 `false-impact-version`：
那等于宣称一个还没发出去的版本有人受害，是与「开发期称修复」相反的另一种失真。

**判据是「缺陷的暴露面」，不是「修复的发布时间」**：缺陷在已发布版本里存在过 → 用户可能已遇到 →
对外可称「修复」，哪怕修它的那个版本还没发出去。

### 前缀与措辞是两条轴

- **前缀 `fix(...)` = 技术性质**：这一条改动消除的是缺陷。它**不宣称影响面**，供检索与计数用。
- **措辞 + 影响面声明 = 受众**：决定能不能出现「修复」二字。

两条轴分开，才不会为了对外好看，把内部记录改得查不到缺陷。

### 为什么不是措辞洁癖

| 方向 | 失真后果 |
|---|---|
| 对外夸大影响面 | 读者去核对一个自己不可能踩到的坑，误判自身风险（虚假告警，与「永久红的闸门」同病） |
| 对内抹掉「修复」 | 后来人不知道这里曾经错过、为什么这么写，改回去的概率上升 |

两个方向同源：**用一套措辞服务两个受众**。

### 渠道清单（判据第 1 条的"已对外分发"指什么）

| 渠道 | 为什么算 | 查法 |
|---|---|---|
| **GitHub `main` 公开源码** | 仓库公开，`git clone` 即得完整代码；**本仓的主渠道** | `git log -1 origin/main` + `git show origin/main:package.json` |
| npm | 装了包的人直接受影响 | `npm view focus-guard versions` |
| GitHub Releases / tags | 有人按 tag 取版本 | `git ls-remote --tags origin` |
| marketplace / 安装包 | 同上 | 人工核对 |

**判据取各渠道最高者。** 只看其中一个会得出相反的结论——本仓就栽过：npm 只到 `3.0.7`，
而 GitHub `main` 已到 `3.1.0`，只查 npm 会把三个已发布的段落误判成开发期。

### 事实基线（2026-11-17 核）

| 渠道 | 当前最高 | 备注 |
|---|---|---|
| npm | `3.5.2`（2026-11-18，OIDC + provenance） | 走 GitHub Actions `publish.yml`；本地 `npm publish` 无 token 必 401，那是设计 |
| **GitHub `main`** | **`3.5.2`**（`854d700`） | 公开源码，clone 即得 |
| GitHub Releases / tags | `v3.5.2` | 2026-11-17 补齐 v3.3.1 / v3.4.1 / v3.5.0；此后逐版打 tag |

→ **对外已分发的最高版本 = `3.5.2`**，三个渠道齐平。齐平是常态，「取最高者」这一步不产生分歧，
但判据不能因此省掉：2026-10-27 那次 npm 落后 GitHub 两个次版本，只查 npm 会把三个已发布段落误判成开发期。

判据已机械校验：`tests/changelog-audience.test.mjs` 的 `PUBLISHED_MAX` 常量。
**发布新版本时改这一个常量**，各段的声明与措辞约束会自动跟着换。

引号约定：写 `「修复」`（加引号）= 在**谈论这个词**（如本节的说明），不算违规；不加引号的「修复」= 在**宣称修了东西**，开发期段里出现即违规。

## 二、什么时候升什么号

> 下表是**发版时**的升法。开发期不跟着改动升号（见下方「版本号与提交」）。

| 触发 | 升法 | 例 |
|---|---|---|
| 累积 **10–30 条**修复（按 CHANGELOG 条目计） | **次版本 +1，补丁归零**：`x.x.0` | `3.4.1` → `3.5.0`（18 条） |
| 未满 10 条、且无严重缺陷 | **补丁 +1** | `3.5.1` → `3.5.2` |
| **严重缺陷**（判据见下） | **立即发补丁，不等攒批** | `3.5.1` → `3.5.2`（装上了不加载） |
| 破坏性行为变更（红线增减、默认档位翻转、许可变更） | 也走 **x.x.0**，并在 CHANGELOG 标「行为变更」 | `3.1.0` |
| 仅文档/注释/测试，无行为变化 | **不升版本**，只记 CHANGELOG | — |
| 发布到 npm | 由人拍板；发布即不可回退（版本号不可复用） | — |

**攒批窗口（2026-11-18 定）**：10 条是**下限不是配额**——不满 10 条就攒着，**满 30 条必须发**。
中间什么时候切，只看缺陷严重程度，不看日期、不看心情。这条替换了原先「满 10 就发」的口径。

**版本号与提交（2026-11-22 定）**：

1. **开发期不升版本**。版本号停在当前值（现 `3.5.3`），只在真正发版动作里按上表升一次；
   「一有改动就 +1」会让版本号变成提交计数器，对外无意义。
2. **一次攒批 = 一次提交**。攒批期内的所有改动并入**同一个提交**（后续改动走 `git commit --amend`），
   不新增提交次数；需要留证据的分段说明写进提交信息正文。
3. 攒批窗口仍按 10–30 条计；只有触发发版（满 30 / 严重缺陷 / 人类拍板）时才动版本号。
4. **推送只在窗口满足或人类明说时发生**。攒批期内**不推**；每修完一处就推 = 把推送当成交付动作，
   等于回到「改一次推一次」。推送前若本地已有多条提交，先 squash 成一条再推。
   2026-11-22 的教训：`2453089` 之后 7 次小修各推一次，违反本条——以后只累计，不逐次推。

**「严重」的判据**（任一条成立即立即发补丁，不攒）：

1. 新用户按文档走完命令后**功能不生效**（装上了不加载 / 加载了不执法）；
2. 已分发版本造成**数据或安全**面损失；
3. **发布链路本身**断了（发不出去，或发出去的内容是错的）。

`3.5.2` 是第一条按第 1 条走的：`postinstall` 让 pnpm 非零退出，dsh 的 bundles 对账被跳过，
新用户装完插件根本不加载——而 `3.5.1` 恰好刚把「从 npm 装」放到文档第一位。

**计数口径**：以 CHANGELOG 中该版本下的 `- fix(...)` / `- feat(...)` 条目数为准（`docs` / `chore` 不计入 10 次）。
一条提交含多个条目时按**条目数**计；`feat` 与 `fix` 同权计入。
**开发期缺陷照计**——计数看的是技术性质（第一节「两条轴」），与对外措辞无关；否则「修得多」反而升不了版，会鼓励把缺陷藏起来不记。

**计数基线（2026-10-22 确定）**：**3.0.9 为基线**，不追溯更早的历史条目。
理由：3.0.8 从未发布 npm，3.0.9 段里混入了 3.0.8 时代的内容（51 条），追溯会把版本号跳到 3.5.0 而对外无意义。

实际执行：

- `3.0.9` 之后累积 **7 条**（fix 3 / feat 4）→ 未满 10，故发 **3.0.10**（补丁号）。
- `3.0.10` 之后累积 **17 条**（fix 12 / feat 5，其中 10 条来自 10-27 质量门自证、7 条来自同轮工具链内置化）→ 满 10，故发 **3.2.0**。
- `3.2.0` 之后累积 **1 条**（fix 1：`plugin_manager` 只读口）→ 未满 10，故发 **3.2.1**（补丁号）。

**2026-11-18 对账**（fix+feat 口径，依次 3.3.0 → 3.5.2）：
**11 / 8 / 91 / 3 / 36 / 2 / 18 / 0 / 2**。也就是说——

- `3.3.2` 攒了 **91 条**、`3.4.0` 攒了 **36 条**，两次都**超过 30 的上限**；
- `3.5.0` 的 **18 条**是唯一落在 10–30 窗口内的次版本；
- 「满 10 就发」**从未被执行过**——实际一直是「攒到收口批次发」。

上面那张表就是把这个既成事实写成规则，而不是继续假装按 10 切。**从 `3.5.2` 起按新口径记账。**

## 三、必须同步的版本面（7 处清单 + 2 个常量 + CHANGELOG）

```
package.json
marketplace.json
.zcode-plugin/plugin.json
.claude-plugin/plugin.json
.claude-plugin/marketplace.json
packages/core/package.json
packages/extended/package.json
packages/core/src/core/constants.mjs        ENGINE_VERSION
packages/core/src/dsh/guard/runtime.mjs      PIPELINE_VERSION（格式 x.y.z-mN）
CHANGELOG.md                                 最新条目（须等于上述版本）
```

验收用例（`tests/acceptance.test.mjs`）已锁：八处清单（含 `package-lock.json`）+ `ENGINE_VERSION` 相同、且等于 CHANGELOG 最新条目（防「一致地落后」）。
**`PIPELINE_VERSION` 不在断言里**——它是热重载的磁盘/内存比对标记（`runtime.mjs` 用它判断"磁盘代码已更新，请重启"），不是发布版本，锁死它只会让每次改 pipeline 都要连带升版。
2026-11-19 核对时发现本文原先把它的位置写成 `src/dsh/pipeline.mjs`，而该文件里没有任何版本常量——**路径存在、符号不在**，`docs:lint` 的路径判据抓不到这一类，只能人读。
`packages/core/hooks/guard.mjs` 是**封存**文件，版本独立，**不参与**升版。

清单里的 `name` / `description` / `displayName` / 两个 i18n 块，曾在 5 份 JSON 里各手写一份。
代价已经付过：自适应 TTL 从四档阶梯改成半衰期之后，`.zcode-plugin/plugin.json` 的简介还写着「4h~7天」，
「上下文污染检测(58条)」的条号也对不上——**改了代码忘改副本，不会有任何闸门报错，因为每份副本都自洽**。

现改为单点派生：

- **真源**：`packages/core/package.json` 的 `description` / `displayName` / `displayNameI18n` / `descriptionI18n`。
  不新开真源文件——为了收敛再加一个 JSON 是本末倒置。
- **副本**：根 `marketplace.json`、`.claude-plugin/marketplace.json`、`.claude-plugin/plugin.json`、`.zcode-plugin/plugin.json`。

## 四、升版动作清单

1. 改上述 7+2 处版本（`PIPELINE_VERSION` 例外：它记的是 pipeline 最后一次改动，热重载靠它比磁盘与内存，不是发布版本，没动就不动）
2. `CHANGELOG.md` 把累积区改为 `## x.y.z · 日期`，条目按 `fix/feat/perf/docs/chore` 前缀。
   **日期填推送当天**（对外发布日），不填动笔日——两者同日时看不出区别，不同日时前者才是
   读者要的那个数。所以本清单第 6 条要求推送与升版同日完成——这不只是省事，它是日期口径成立的前提。
3. 按第一节标**影响面**：整段未对外分发 → 段首写 `> **影响面：开发期**`，且正文不出现「修复」；已发布 → 写「修复」+ 影响面
4. 面向使用者的改法同步 `README.md` / `README.zh-CN.md` / `INSTALL.md`
5. `npm run check`（含 schema 指纹、真实夹具回归、等变矩阵、受众口径）；全绿才允许提交
6. 本地提交；**攒批期内所有改动并入同一提交**（新改动用 `git commit --amend`，不新增提交次数），
   一次攒批只留一个提交。**推送随攒批窗口**——按 §一 的「10 条下限 / 30 条上限」一次推，
   不满 10 条只留本地提交；不再按每天 20:00 定点推。推送时 pre-push 钩子会强制跑 `npm run check`。
7. **打 tag + 建 Release**——这一步本身就是 npm 发布。`publish.yml` 由 `release: published` 触发，
   建 Release 就等于发 npm：
   ```bash
   git tag -a vX.Y.Z -m "..." && git push origin vX.Y.Z
   gh release create vX.Y.Z --title "vX.Y.Z · YYYY-MM-DD" --notes-file <说明>
   gh release edit vX.Y.Z --latest      # 钉住 Latest，见下
   ```
   **只跑 `workflow_dispatch` 会漏掉 Release 对象**——2026-11-17 的 3.5.0 就是这么漏的：
   npm 上有了、GitHub 上没有。反过来漏了也能补建，`publish.yml` 的守卫会在「registry 已有该版本」时跳过发布。
   `gh release create` 会把**最后创建的那个**标成 Latest，补建历史版本时会抢走标记，所以补完要重钉。
   核验：`npm view focus-guard dist-tags`。npm 打印 `+ pkg@ver` 只是「已接收」，
   registry 还要过两三分钟处理流水线；`publish.yml` 的 Verify 现在轮询到出现为止，读不到即红。
8. **回填 npm 版本声明**（三处，闸门查不到）：根 `README.md` 的版本口径行、两份包 README 的版本表。
   `docs:lint` 不上网，这三处只能人工同步——2026-11-17 实测漏了一整轮，文档写 `3.3.3` 时 npm 已经是 `3.4.1`。
