# 版本策略（RELEASE-POLICY）

> **状态**：权威 · 适用版本 3.3.0 · 最后核对 2026-10-28

> 人类批示 2026-10-22：**每 10 次修复合为一次变更（x.x.0）；其余按补丁号递增**。

## 一、「修复」的定义（受众判据）

> 人类批示 2026-10-27：**对外文档的「修复」默认指「修复用户可能已经遇到的问题」。**

对外文档写「修复某某问题」，等于向读者宣称一件事：**你可能已经踩过这个坑**。所以这三个字有门槛，三条同时成立才算：

| # | 条件 | 判据 |
|---|---|---|
| 1 | 缺陷存在于**已对外分发**的版本 | 版本号 ≤ **各对外渠道的最高版本**（见下方「渠道清单」，取最高者） |
| 2 | 用户有路径真的遇到 | 能在该渠道的公开产物上复现，不依赖只在本地未推送代码里存在的东西 |
| 3 | 修完之后对外可见行为变了 | 用户升级后能感知到差异 |

不满足第 1 条的叫**开发期缺陷**：在尚未发布的版本里被发现并处理掉。
它**不是「不算修复」**——技术上就是修复；它只是**没有用户受害**。

### 处置

| 场景 | 对外文档（`CHANGELOG.md` / Release Notes / `README*`） | 内部台账（`docs/HANDOFF-*.md`） |
|---|---|---|
| 缺陷在已发布版本里 | 写「修复」+ 影响面（哪些版本、什么症状） | 写「修复」+ 根因 + 证据 |
| 缺陷在未发布版本里 | **不写「修复」**：写「某某改为…／收敛为…／加固…」+ 事实 | 照写「修复」，注明「开发期，未发布」 |
| 不是缺陷（新增能力／重构／测试） | 按性质写 `feat` / `refactor` / `test` | 同 |

### 标注粒度：段级 vs 条目级

| 段落情况 | 怎么标 | 本仓实例 |
|---|---|---|
| 整段都只在未推送的代码里存在过 | 段首写 `> **影响面：开发期**` | 同质段落，省得逐条标 |
| 段内混合：有的修已发布版本的缺陷、有的是开发期新造的东西 | 逐条标 `〔开发期〕`（开发期那条）与 `〔影响面：x.y.z〕`（已发布那条） | **`3.2.0`**：熔断 / 抽查B / 审计重复记账 修的是 `3.1.0`（已推 GitHub）里的问题；工具链四件是当天新造。**`3.3.0`**：两条 `fix` 标 `〔影响面：3.2.1〕`，其余为新增能力 |

**未发布段的每条 `fix` 必须二选一自报影响面**，缺一条就报 `unattributed-fix`。
判据从段级改成逐条（2026-10-30，执行层结论，待批示）有两个原因：

1. **段级会放过**：段里只要有一处 `〔开发期〕` 就算合规，同段另一条开发期缺陷照样能写「修复」。
2. **段级会误报**：`3.3.0` 段一条开发期缺陷都没有（两条 fix 改的是已推 `3.2.1` 里的 `notePrefixShift`
   盲区与 `MAX_RENDER=1200` 裁剪，两者都在 `origin/main` 上），却被报「一处标注都没有」——
   两种完全不同的情形压成同一句红，红得没信息量。

`〔影响面：x.y.z〕` 里的版本必须 ≤ 已分发最高版，写高了报 `false-impact-version`：
那等于宣称一个还没发出去的版本有人受害，是与「开发期称修复」相反的另一种失真。

**判据是「缺陷的暴露面」，不是「修复的发布时间」**：缺陷在已发布版本里存在过 → 用户可能已遇到 →
对外可称「修复」，哪怕修它的那个版本还没发出去。

### 前缀与措辞是两条轴

- **前缀 `fix(...)` = 技术性质**：这一条改动消除的是缺陷。它**不宣称影响面**，供检索与计数用。
- **措辞 + 影响面声明 = 受众**：决定能不能出现「修复」二字。

两条轴分开，才不会为了对外好看，把内部记录改得查不到缺陷。

### 为什么不是措辞洁癖

| 方向 | 失真后果 |
|---|---|
| 对外夸大影响面 | 读者去核对一个自己不可能踩到的坑，误判自身风险（虚假告警，与「永久红的闸门」同病） |
| 对内抹掉「修复」 | 后来人不知道这里曾经错过、为什么这么写，改回去的概率上升 |

两个方向同源：**用一套措辞服务两个受众**。

### 渠道清单（判据第 1 条的"已对外分发"指什么）

| 渠道 | 为什么算 | 查法 |
|---|---|---|
| **GitHub `main` 公开源码** | 仓库公开，`git clone` 即得完整代码；**本仓的主渠道** | `git log -1 origin/main` + `git show origin/main:package.json` |
| npm | 装了包的人直接受影响 | `npm view focus-guard versions` |
| GitHub Releases / tags | 有人按 tag 取版本 | `git ls-remote --tags origin` |
| marketplace / 安装包 | 同上 | 人工核对 |

**判据取各渠道最高者。** 只看其中一个会得出相反的结论——本仓就栽过：npm 只到 `3.0.7`，
而 GitHub `main` 已到 `3.1.0`，只查 npm 会把三个已发布的段落误判成开发期。

### 事实基线（2026-10-27 核）

| 渠道 | 当前最高 | 备注 |
|---|---|---|
| npm | `3.0.6` / `3.0.7` | 发的很少，不是主渠道 |
| **GitHub `main`** | **`3.1.0`**（2026-10-26，`5f0e7e5`） | 公开源码，clone 即得 |
| GitHub Releases / tags | `v3.0.4` | 3.0.9+ 未打 tag，但源码在 `main` 上 |

→ **对外已分发的最高版本 = `3.1.0`**。故 `3.0.9` / `3.0.10` / `3.1.0` 三段属**已发布**（可用「修复」）；
`3.2.0` 尚未推送，但它属**混合段**——其中 3 条修的是 `3.1.0` 里的问题（对外），9 条是当天新造工具/测试的缺陷（开发期，已逐条标 `〔开发期〕`）。

⚠️ 本次核验的局限：环境连不上 `api.github.com`（TLS 错误），GitHub 侧取自本地 `origin/main` 引用
（最后一次 fetch 的状态）。**若远端已更靠前，须上调 `PUBLISHED_MAX`。**

判据已机械校验：`tests/changelog-audience.test.mjs` 的 `PUBLISHED_MAX` 常量。
**发布新版本时改这一个常量**，各段的声明与措辞约束会自动跟着换。

引号约定：写 `「修复」`（加引号）= 在**谈论这个词**（如本节的说明），不算违规；不加引号的「修复」= 在**宣称修了东西**，开发期段里出现即违规。

## 二、什么时候升什么号

| 触发 | 升法 | 例 |
|---|---|---|
| 累积 **10 次修复**（按 CHANGELOG 条目计） | **次版本 +1，补丁归零**：`x.x.0` | `3.0.9` → `3.1.0` |
| 单次修复 / 小改动（未满 10 次） | **补丁 +1** | `3.0.8` → `3.0.9` |
| 破坏性行为变更（红线增减、默认档位翻转、许可变更） | 也走 **x.x.0**，并在 CHANGELOG 标「行为变更」 | `3.1.0` |
| 仅文档/注释/测试，无行为变化 | **不升版本**，只记 CHANGELOG | — |
| 发布到 npm | 由人类批示；发布即不可回退（版本号不可复用） | — |

**计数口径**：以 CHANGELOG 中该版本下的 `- fix(...)` / `- feat(...)` 条目数为准（`docs` / `chore` 不计入 10 次）。
一条提交含多个条目时按**条目数**计；`feat` 与 `fix` 同权计入。
**开发期缺陷照计**——计数看的是技术性质（第一节「两条轴」），与对外措辞无关；否则「修得多」反而升不了版，会鼓励把缺陷藏起来不记。

**计数基线（2026-10-22 人类批示后确定）**：**3.0.9 为基线**，不追溯更早的历史条目。
理由：3.0.8 从未发布 npm，3.0.9 段里混入了 3.0.8 时代的内容（51 条），追溯会把版本号跳到 3.5.0 而对外无意义。

实际执行：

- `3.0.9` 之后累积 **7 条**（fix 3 / feat 4）→ 未满 10，故发 **3.0.10**（补丁号）。
- `3.0.10` 之后累积 **17 条**（fix 12 / feat 5，其中 10 条来自 10-27 质量门自证、7 条来自同轮工具链内置化）→ 满 10，故发 **3.2.0**。
- `3.2.0` 之后累积 **1 条**（fix 1：`plugin_manager` 只读口）→ 未满 10，故发 **3.2.1**（补丁号）。
- 下次基线从 3.2.1 起算，满 10 条时升 **3.3.0**。

## 三、必须同步的版本面（7 处清单 + 2 个常量 + CHANGELOG）

```
package.json
marketplace.json
.zcode-plugin/plugin.json
.claude-plugin/plugin.json
.claude-plugin/marketplace.json
packages/core/package.json
packages/extended/package.json
packages/core/src/core/constants.mjs        ENGINE_VERSION
packages/core/src/dsh/pipeline.mjs           PIPELINE_VERSION（格式 x.y.z-mN）
CHANGELOG.md                                 最新条目（须等于上述版本）
```

验收用例（`tests/acceptance.test.mjs`）已锁：七处清单 + `ENGINE_VERSION` 相同、且等于 CHANGELOG 最新条目（防「一致地落后」）。
`packages/core/hooks/guard.mjs` 是**封存**文件，版本独立，**不参与**升版。

## 四、升版动作清单

1. 改上述 7+2 处版本（`PIPELINE_VERSION` 例外：它记的是 `pipeline.mjs` 最后一次改动，本文件没动就不动）
2. `CHANGELOG.md` 把累积区改为 `## x.y.z · 日期`，条目按 `fix/feat/perf/docs/chore` 前缀
3. 按第一节标**影响面**：整段未对外分发 → 段首写 `> **影响面：开发期**`，且正文不出现「修复」；已发布 → 写「修复」+ 影响面
4. 面向使用者的改法同步 `README.md` / `README.zh-CN.md` / `INSTALL.md`
5. `npm run check`（含 schema 指纹、真实夹具回归、等变矩阵、受众口径）；全绿才允许提交
6. 本地提交；**推送只在每天 20:00 批次**（人类批示）
