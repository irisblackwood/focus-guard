# 动笔前拆解（focus-plan）

> **状态**：权威 · 适用版本 3.5.3 · 最后核对 2026-11-26

## 0. 这一份解决什么

模糊请求直接动笔，代价不是「做错」，是**做对了也不是他要的**。
返工的成本远高于先问三句话。

判据：一个请求模糊不模糊，不看长短，看**有没有说清怎么算完成**。

- 「把首页改得好看点」——没有。
- 「首页首屏从 3 屏压到 1 屏，标题字号 32→40」——有。

**有验收判据的任务不需要本技能，直接做。** 本技能只服务一种情形：动笔前想不清终点。

## 1. 问清（一次一问，最多三问）

先看再问：读相关文件、看最近提交、看仓库已有约定。**能从代码里读出来的不要问**——
问之前没看一眼，是最容易被记恨的那种提问。

只问三件事，按顺序：

1. **目的**：解决谁的什么问题？（不是「要什么功能」）
2. **边界**：哪些明确不做？（不做的清单比做的清单更有用）
3. **验收**：怎么算完成？给一个可观测信号——一条命令、一个数字、一张截图、一个行为。

一次只问一个。三个一起抛，对方只会回答最容易的那个，然后你会以为另外两个已经答了。

## 2. 给路线，不给方案

至少两条，每条一句话说清代价；带推荐，并说清为什么不选另一条。

只给一条，等于把决策原样推回去——那这一步就白做了。

## 3. 拆步（每步 2-5 分钟）

一步一个动作，每步都能独立验证：

- 写一条会失败的测试 → 跑它，确认真的红 → 写最小实现 → 跑它，确认绿 → 提交
- 改一处文案 → 跑那条卡它的判据 → 提交

**每条步骤必须带验收判据**（命令 + 期望输出）。写不出判据的步骤，说明还没想清，回第 1 步。

## 4. 落盘

写到 `docs/plans/YYYY-MM-DD-<slug>.md`；仓库已有计划目录就跟着走，别另起一套。

```markdown
# <主题>

**目的**：一句话
**不做**：一句话
**验收**：一条可观测信号

## 步骤
1. <动作> —— 验收：`<命令>`，期望 <输出>
2. ...
```

## 5. 什么时候停

计划写到「能交给别人照做」就够。继续加细节是**用计划代替执行**——
把完整代码写进计划，等于在脑子里跑了一遍而一次也没验证。

## 6. 与动笔闸的关系

focus-guard 的动笔闸（`guard/writing-gate.mjs`）在「模糊开发任务 + 首次改文件」时 deny 一次，
要求先加载方法论技能。**本技能就是它认的那一个，随包自带，不依赖任何外部技能。**

装了 superpowers 的用户，`brainstorming` / `writing-plans` 同样被认；
装了别家方法论技能的（`planning` / `design-spec` 这类名字），按名字形态也认。
